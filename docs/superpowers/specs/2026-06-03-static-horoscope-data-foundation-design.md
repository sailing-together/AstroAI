# Static Horoscope Data Foundation Design

> Date: 2026-06-03
> Status: Proposed design for review
> Target branch: `v2`

## Expert Meeting Conclusion

AstroAI should continue with a static-first public horoscope model and reserve live AI calls for personalized registered-user features. Public visitors should be able to choose a zodiac sign or enter a birth date, then read stored 2026 horoscope guidance without registration and without triggering an AI request at page-view time.

The next backend milestone should make stored horoscope data the source of truth. The current JSON/dev seed path is useful for development, but it should become an importer or generator boundary rather than the long-term persistence model.

## Product Rules

- Public horoscope reads are free, anonymous, and static.
- The public frontend loads one sign/year bundle, then derives the selected day, matching week, matching month, and year overview locally.
- The production public page should not show long weekly lists. Weekly content is date-driven.
- The only live AI request paths in MVP are registered-user personalization, AI Astrologer chat, AI natal chart interpretation, and explicit backend generation jobs.
- Development seed data may be generated by Codex-authored deterministic logic for local testing.
- Production static content generation should be a backend job that calls the selected AI provider once per sign/period batch, stores rows, and serves future reads from the database/cache.
- Knowledge-base references must come from public-domain, open-licensed, self-authored, or otherwise legally approved sources. Do not download or embed copyrighted astrology books without permission.

## Scope

This design covers the backend static horoscope data foundation for 2026.

Included:

- Optimized database shape for yearly, monthly, weekly, and daily public horoscope rows.
- 2026 full-year generation coverage for all 12 zodiac signs and 9 focus dimensions.
- API read behavior for sign/year bundles and date-driven period lookup.
- Development seed/import behavior.
- Knowledge-base/RAG boundary for future generation quality.
- Frontend display contract for selected date behavior.

Excluded from this phase:

- Final public UI redesign.
- Auth, billing, and registered-user dashboards.
- Live personalized prediction implementation.
- Full vector-search RAG implementation.
- Downloading copyrighted books or proprietary knowledge bases.

## Data Coverage

For target year `2026`, each zodiac sign should have stored rows for all supported focuses:

- `general`
- `love`
- `career`
- `money`
- `wellness`
- `social`
- `family`
- `study`
- `mood_energy`

Per sign, the expected 2026 coverage is:

| Period | Rows per focus | Rows per sign with 9 focuses | Rule |
|---|---:|---:|---|
| Yearly | 1 | 9 | One row dated `2026-01-01` |
| Monthly | 12 | 108 | First day of each month |
| Weekly | All ISO weeks intersecting 2026 | 477 if 53 weeks | Week starts can include `2025-12-29` for the week containing `2026-01-01` |
| Daily | 365 | 3,285 | Every calendar day in 2026 |

Total per sign for 2026: `3,879` rows if 53 weekly rows are stored.

Total for all 12 signs: `46,548` rows.

The weekly rule is intentionally "weeks intersecting the target year," not "Mondays inside the target year." This prevents the selected date `2026-01-01` from missing its weekly reading.

## Database Design

The canonical table remains `static_horoscopes`, but the implementation should optimize the current model before production data generation.

Recommended columns:

| Column | Type | Notes |
|---|---|---|
| `id` | uuid primary key | Content id |
| `sign` | zodiac_sign/text not null | Canonical lowercase sign |
| `target_year` | integer not null | Bundle year, e.g. `2026` |
| `period` | horoscope_period/text not null | `daily`, `weekly`, `monthly`, `yearly` |
| `focus` | horoscope_focus/text not null | One of the 9 supported dimensions |
| `content_date` | date not null | Day date, month start, week start, or year start |
| `period_end_date` | date | Optional but recommended for weekly/monthly lookup clarity |
| `title` | text not null | Display title |
| `summary` | text not null | Short scannable summary |
| `body` | text not null | Full reading copy |
| `lucky_numbers` | integer[] | Optional |
| `lucky_color` | text | Optional |
| `source` | text not null | `codex-dev`, `ai-batch`, `manual`, or `imported` |
| `generation_model` | text | `codex-dev`, `gemini-2.5-flash-lite`, etc. |
| `prompt_version` | text | Generation prompt version |
| `knowledge_version` | text | Knowledge/reference pack version used |
| `content_version` | integer not null | Incremented when regenerated |
| `is_active` | boolean not null | Allows old generated rows to be retained |
| `generated_at` | timestamptz not null | Generation timestamp |
| `created_at` | timestamptz not null | Row creation time |
| `updated_at` | timestamptz not null | Last update time |

Recommended uniqueness:

```sql
unique (sign, target_year, period, focus, content_date, content_version)
```

Recommended active-row guard:

```sql
unique (sign, target_year, period, focus, content_date)
where is_active = true
```

This improves on the current unique identity by making `target_year`, source tracking, content versioning, and regeneration history explicit.

## API Design

Keep the existing public route family:

- `GET /api/v1/horoscope/bundle/{sign}?year=2026`
- `GET /api/v1/horoscope/daily/{sign}?date=2026-06-03&focus=general`
- `GET /api/v1/horoscope/weekly/{sign}?week=2026-W23&focus=general`
- `GET /api/v1/horoscope/monthly/{sign}?month=2026-06&focus=general`
- `GET /api/v1/horoscope/yearly/{sign}?year=2026&focus=general`
- `GET /api/v1/utils/sun-sign?birth_date=1994-06-14`

Bundle read behavior:

1. Validate sign and target year.
2. Read active rows from database/cache only.
3. Return all rows needed for the sign/year bundle.
4. Do not call any AI provider.
5. If rows are missing in development, allow the Codex dev generator/importer to populate local data.
6. If rows are missing in production, return a clear data-not-ready error or fall back to a known active previous version only when explicitly configured.

The bundle response can remain arrays for frontend compatibility, but each entry should include enough metadata to support debugging and future cache rules:

```json
{
  "sign": "Gemini",
  "year": 2026,
  "daily": [],
  "weekly": [],
  "monthly": [],
  "yearly": [],
  "source": "static",
  "generated_at": "2026-01-01T00:00:00Z"
}
```

## Date Selection Rules

The frontend selected date drives all public readings:

- Daily: exact selected date.
- Weekly: row whose `content_date <= selected_date <= period_end_date`.
- Monthly: first day of selected date's month.
- Yearly: `YYYY-01-01`.

For 2026, `2026-01-01` should map to weekly row `2025-12-29` through `2026-01-04` while still belonging to the `2026` bundle.

The public UI should display only the selected date's:

- Daily reading.
- Matching weekly reading.
- Matching monthly reading.
- Yearly overview.

The monthly list may be available later as a planning/browse view, but it should not block the main reading experience.

## Generation Design

### Development Mode

Development mode may use Codex-authored deterministic seed generation.

Rules:

- Generate rows for all 12 signs and all 2026 periods when explicitly requested.
- Seed text should be reader-facing and should not mention Codex, Gemini, providers, or implementation details in visible horoscope copy.
- Seed data may use `source = "codex-dev"` and `generation_model = "codex-dev"` metadata.
- Generated files should not use provider names in filenames.
- Local dev generation should be repeatable so tests can assert row counts and date coverage.

### Production Mode

Production generation should use backend jobs.

Recommended jobs:

- `generate_static_horoscope_year(year)`
- `generate_static_horoscope_sign_year(sign, year)`
- `refresh_static_horoscope_period(sign, period, date_or_year)`
- `validate_static_horoscope_coverage(year)`

Annual generation should preload:

- Yearly rows.
- 12 monthly rows.
- All ISO weeks intersecting the target year.
- All daily rows.

The job should store generated content before any public page depends on it. User page reads must not call any live AI provider.

## Knowledge Base and RAG Boundary

The first implementation should create a knowledge-source boundary without building heavy RAG immediately.

Recommended first tables or files:

- `astrology_knowledge_sources`: source metadata, license, URL/path, version, approval status.
- `astrology_knowledge_cards`: short self-contained reference cards with topic, signs, planets, houses, aspects, and text.

Allowed sources:

- Public-domain astrology texts.
- Open-licensed educational material.
- Self-authored AstroAI editorial notes.
- Licensed material explicitly approved for use.

Blocked sources:

- Copyrighted books copied from the internet.
- Proprietary content from competitors.
- User-private content in public generation prompts.

RAG should support generation quality by providing reference context to scheduled generation jobs. It should not become a runtime dependency for anonymous public reads in MVP.

## Frontend Contract

The production frontend should:

- Default to current year `2026` during this data phase.
- Let users choose a sign directly.
- Let users enter a birth date to calculate Sun sign.
- Let users choose a 2026 date.
- Load one bundle per sign/year.
- Derive daily, weekly, monthly, and yearly entries from the loaded bundle.
- Show clear loading and data-not-ready states.
- Avoid provider names and backend/debug terminology in the user-facing UI.

The current `frontend/preview` page remains a backend/API tester only.

## Roadmap

### Phase A: Spec and Plan

- Finalize this design.
- Update `SCHEMA.md`, `API_SPEC.md`, `ARCHITECTURE.md`, and `FRONTEND_SPEC.md` only if this design changes their canonical rules.
- Write an implementation plan with exact files and tests.

### Phase B: Database Foundation

- Add/adjust SQLAlchemy model fields for `target_year`, `period_end_date`, source/version metadata, and active-row uniqueness.
- Add repository methods for coverage validation and date-driven lookup.
- Add tests for 2026 row counts and weekly edge dates.

### Phase C: Dev Generation and Import

- Generate all 2026 static rows for all 12 signs in development.
- Support writing generated rows into the database.
- Keep JSON seeds optional as fixtures/import sources, not source of truth.

### Phase D: API and Frontend Alignment

- Ensure bundle and period endpoints read database-backed content.
- Ensure frontend uses selected date to display daily, matching week, matching month, and year.
- Keep public reads free of live AI calls.

### Phase E: Production Generation Boundary

- Add generation job interfaces.
- Add prompt versioning and knowledge versioning.
- Add coverage validation before publishing a generated year.

## Open Risks

- Generating 46,548 rows for 2026 is manageable, but prompt batching and editorial quality need constraints.
- Bundle payload size may become large. The first implementation can load one full sign/year bundle; later optimization can split daily rows by month or cache aggressively if payload size hurts UX.
- Weekly boundary logic must be tested carefully around January 1 and December 31.
- RAG source licensing must be tracked from the beginning to avoid legal and trust problems later.

## Acceptance Criteria

- The spec consistently uses `2026` as the target year.
- Public horoscope reads never call live AI.
- The database is the production source of truth.
- Development can generate initial rows with Codex-authored deterministic seed logic.
- 2026 weekly coverage includes all weeks intersecting 2026.
- Frontend display rules are date-driven and show only daily, matching weekly, matching monthly, and yearly content.
- Knowledge-base/RAG is defined as a generation aid, not a runtime public-read dependency.
